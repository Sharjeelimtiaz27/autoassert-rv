Assertion Quality Ranker

A beginner's guide to how we measure whether a hardware security check is actually good. It covers the idea, the three metrics with real Ibex examples, what other researchers have done, what our red-team and blue-team reviews found, and the experiments still to run.

Start here

The idea in five steps

Step 1A processor

Ibex is a small open-source RISC-V processor. Its design is written as code (RTL).

Step 2Security checks

We already have 68 assertions: small rules such as "user programs may not change machine registers". All 68 are proven true on Ibex (our BEC 2026 paper).

Step 3Are the checks good?

A check can be true and still weak: it may watch only one way of breaking the rule. Nobody has a formal way to say how strong each check is.

Step 4Give each a score

Three metrics, computed by the JasperGold tool on the clean design, give every assertion a quality score called AQS.

Step 5Test the score

We hide 39 hardware Trojans in Ibex. If high-scoring assertions catch more Trojans, the score is meaningful.

Why it matters: a chip designer can then say "this set of checks covers our security logic well", or see exactly which checks are weak and what to add.

Vocabulary

Key words in plain language

RTL
The code that describes a chip's circuits, written in SystemVerilog.
Assertion
A rule written in code that must always hold, e.g. "in user mode, never write mstatus". If it is broken, the assertion "fires".
JasperGold
A Cadence tool that checks rules mathematically, for every possible input, instead of running test cases.
FPV
Formal Property Verification. The JasperGold mode that asks "can any input sequence break this rule?"
SPV
Security Path Verification. The JasperGold mode that asks "can data travel from here to there through the circuit?"
Proven / counterexample
Proven means the rule can never break. A counterexample (CEX) is a concrete step-by-step case where it does.
Cone of influence (COI)
All the circuit logic that can affect an assertion. It is the part of the design the assertion "sees".
Hardware Trojan
A small malicious change hidden in a chip design, e.g. a backdoor that grants machine privileges.
Non-vacuous
The assertion's "if" part can actually happen, so it is not passing only because it never gets tested.
mstatus
An Ibex machine-mode control register. Changing it from user mode would be a privilege attack.

Metric 1 · Security RTL Coverage (SRTLC)

JasperGold COI report · 0 new runs

How much of the security logic do our checks look at?

Everyday picture

A bank has 40 important doors. The security cameras (assertions) can see 30 of them. Coverage is 30 / 40 = 75%. The other 10 doors are unwatched.

  1. Which code lines are "security logic"? Those that drive signals named in the expert NS31A security properties. We don't guess them.
  2. JasperGold reports each assertion's cone of influence: the lines it can see.
  3. Count the security lines that at least one assertion sees.
SRTLC = security lines seen by some assertion ───────────────────────────────── × 100% all security lines in the module

Review note: COI coverage can overestimate what an assertion really checks. Both review teams suggest also reporting proof-core coverage, a stricter JasperGold option.

Metric 2 · Assertion Evasion Resistance (AER)

JasperGold FPV + test signal · 10 runs

Can someone break the security rule without this check noticing?

Everyday picture: testing a smoke alarm

The goal is that the kitchen never burns unnoticed. The smoke alarm is our check. To test it properly, we let a helper start a small fire anywhere, at any time, in any way. If the kitchen can burn while the alarm stays quiet, the alarm is weak. If every fire, in every place, sets it off, the alarm is strong.

In AER, JasperGold plays the helper, and it tries every possibility, not just a few.

The three players (real Ibex example)

The security rule (P)

What must never happen. This is the goal, written once.

In user mode, mstatus
must never change.
The assertion under test (A)

One of our 68 checks. AER scores this one.

UserMode && CsrWriteOp
  |-> !WriteEn_mstatus

"If user mode AND a CSR write instruction, then the mstatus write-enable is 0."

The test signal

An extra input JasperGold controls freely. It can flip the mstatus write-enable wire on any clock cycle.

we_seen = we_real XOR test_sig

JasperGold then asks one question: is there any way to set the test signal so that rule P breaks while assertion A stays silent?

In cycle 2 the write-enable is flipped directly, without any CSR instruction. The "if" part of A (CsrWriteOp) is false, so A never checks anything, and mstatus changes in user mode unnoticed. JasperGold shows this exact trace, which tells us precisely why A is weak: it watches the instruction, not the register.

Stronger assertion
UserMode |-> mstatus == $past(mstatus)

"In user mode, mstatus keeps its previous value", whatever caused the change.

Whenever the test signal breaks rule P, this assertion fires, because it watches the register itself. JasperGold checks every possible flip pattern; if no silent break exists, AER = 1.

AER = 1 if no test-signal pattern breaks rule P while A stays silent AER = 0 if JasperGold finds one (and shows the exact trace)

Important: rule P and assertion A must be different. If we used A as its own rule, A could never "break silently" and every assertion would score 1. The review teams suggest taking P from the original NS31A expert property. This is a decision for us (see decisions). Metric 3 · Security Assertion Path Coverage (SAPC)

JasperGold SPV · 10 runs

Are there roads into the security register that no alarm is watching?

Everyday picture

Eight roads lead to the vault (mstatus). For each road we ask whether a car on it would trigger any alarm. Six roads would, two would not. SAPC = 6 / 8 = 75%.

  1. JasperGold SPV lists every path from a chip input to a security register.
  2. For each path, check whether a change travelling along it reaches some assertion.
  3. Paths that reach no assertion are blind spots.
SAPC = paths into security registers watched by an assertion ────────────────────────────────────────────────── × 100% all paths into security registers

How it differs from AER: AER only flips the one wire the test signal is attached to. SAPC looks at all roads, including ones AER never touched.

Problem the review found, and the fix

If "watched" just means "the road lies inside the assertion's cone of influence", every assertion that looks at mstatus automatically watches all roads into it. The number would be almost always 100% or 0% and would just repeat SRTLC.

Fix: for each road, ask SPV whether a change sent down it actually travels through mstatus all the way to the assertion's failure output. This follows the method of our co-author's earlier work (Eslami, Ghasempouri, Pagliarini, 2022).

Putting it together

The Assertion Quality Score (AQS)

Each metric gives a number between 0 and 1 for every assertion. AQS is their average:

AQS = (SRTLC part + AER + SAPC part) / 3

How we check the score works: after scoring, we run the same 68 assertions against 39 Trojan-infected versions of Ibex and count how many Trojans each one catches. If assertions with higher AQS catch more Trojans, the score predicts real protection. Statistically this is a correlation; the reviews recommend Spearman's rank correlation with confidence intervals.

Beside the score: two descriptive tables

Table A: which known weakness each assertion protects against (CWE number and its CVSS severity, following NIST CSWP 45).
Table B: which Trojan types each assertion targets (Availability, Covert, Denial of Service, Integrity, Leak, Privilege). These describe the assertions; they are not part of the score.

What other researchers have already done

Our literature survey found work close to every one of our metrics. That is normal. It tells us which ideas to credit and where our contribution really lies. The papers below are the most important, grouped by the question they answer.

Closest to AER

"Does the check notice when the design is changed?"

Chockler, Kupferman, Vardi et al., 2001Change the design slightly (mutation) and see whether the property notices. The classic idea behind AER.
Kupferman, CONCUR 2006"Sanity checks" after a proof: vacuity and coverage. The framing for our whole paper.
Krishnamurthy et al. 2026 (arXiv 2606.21451); HierSVA 2026 (arXiv 2606.13706)Score LLM-written assertions by how many injected faults they catch.For us: AER differs because it checks all flip patterns in one proof, against a security rule.
Chuah, Appold, Leinmüller: MBMV 2024; RISC-V Summit Europe 2025; ISQED 2026 (ISQED page)Formal Trojan detection on a RISC-V core with Jasper. The red team found the same "XOR free input" trick in their 2025 abstract.For us: cite them as the origin of the mechanism; our addition is a score per assertion.
Closest to SAPC

"Can a change travel to the check?"

Eslami, Ghasempouri, Pagliarini, ISQED 2022 (arXiv 2201.01130)Uses JasperGold SPV to count how many circuit points can reach each assertion ("Security Coverage") and ranks assertions by it. Scores were about 5–7% because they divide by the whole circuit.For us: our own group's work. SAPC narrows it to security registers and tests it against Trojans.
Eslami et al., SCARF, IEEE Trans. Computers 2024 (arXiv 2402.12162)Journal version of the same per-assertion security coverage.
Meza & Kastner, 2023 (arXiv 2304.08263)Coverage metrics based on how information flows through hardware.
Closest to SRTLC

"How much of the design does the check see?"

JasperGold coverage app (Cadence)Built-in cone-of-influence and proof-core coverage. Cadence's own material says COI overestimates.For us: SRTLC's new part is counting only expert-flagged security lines. Also report proof-core.
LAsset (DATE 2026); SAIF (VTS 2021)Find which signals are security "assets". This decides what counts as security logic.
Closest to AQS ranking and our validation

"Which checks are best, and do they catch Trojans?"

Imtiaz, Reinsalu, Ghasempouri, ISCAS 2025 (arXiv 2502.10194)Our own earlier paper: Ibex assertions tested on Trojans with the TDER and TPI measures.For us: reuse and cite TDER/TPI; don't present them as new.

The four problems to solve

Must fix · SAPC

SAPC may count nothing new

Measured with the cone of influence, any assertion that looks at a register "watches" every road into it.

Fix: count only roads where SPV shows a change really reaches the assertion's failure output.

Major · AER

Which rule is P?

If P is the assertion itself, AER is always 1. A fully free test signal may also make almost every assertion score 0.

Fix: take P from the NS31A expert property; score how many flip points or how much tampering the assertion catches (graded).

Major · validation

The Trojan test could look rigged

We wrote the Trojans ourselves, the sample is small, and refinement would be tested on the same Trojans that guided it.

Fix: freeze the Trojans first, keep some aside for the final test, compare with simple baselines.

Major · positioning

No "first" claims

Every single metric has a close ancestor in the literature.

Fix: credit Chuah and Eslami openly and claim the combination plus validation.

Our honest contribution

What we can claim

Proposed novelty sentence (blue team): AQS is a per-assertion security quality score computed by formal analysis on Trojan-free RTL, combining coverage of expert-defined security signals (SRTLC), FPV-based evasion resistance (AER) and SPV-based functional-path coverage (SAPC). On 68 proven Ibex assertions across 9 security modules, AQS computed before any Trojan exists correlates with detection on an independent 39-Trojan benchmark, and AQS-guided refinement improves detection on held-out Trojans.

  • Safe to say: "to our knowledge, the first to combine FPV evasion and SPV path evidence in one per-assertion score".
  • Our cleanest new insight, if the data shows it: an assertion can be behaviourally strong (AER high) and still leave roads unwatched (SAPC low).
  • Never say: "first metric", "first RISC-V Trojan benchmark", or that AQS "proves" detection. Say "correlates with".
